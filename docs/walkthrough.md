# 这个项目在讲什么

一句话：用 2040 张花图教会电脑认 102 种花，并说清楚「为什么能教会」——靠的是从 ImageNet 借来的本事，不是从零学。

对照组专门回答「不借会怎样」：同样 2040 张图，从随机初始化开始训 120 轮，测试准确率只有 **55.46%**，而且训练集上已经 99.5%、验证集 65%、测试集 55%——它把训练图背下来了，没学会认花。

而只借 ImageNet 权重、只训最后一层、12 轮、2 分钟，就到 **81.27%**。

这中间的 26 个百分点，就是「迁移学习借来的东西」的价格。

# 一、这批数据为什么「刁难人」

官方划分：

| 划分 | 数量 | 用途 |
|---|---|---|
| train | 1020（每类 10 张） | 训练 |
| val | 1020（每类 10 张） | 调参 |
| test | 6149 | 最终考试 |

每类只有 10 张训练图，这是最要命的地方。102 类里有的花全数据集只有 40 张，有的 258 张，类别极不均衡。

做法是把 train+val 合成 **2040 张**，每类抽 3 张当验证，变成 **1734 训练 / 306 验证**，test 6149 张只在最后用一次。

为什么不直接从 train 训、val 验？每类 10 张里再切 3 张，训练只剩 7 张，太少。合并后每类 20 张，抽 3 张验、17 张训，是「验证可信」和「训练够用」之间的折中。

# 二、迁移学习到底「借」了什么

ResNet-18 有 **11,228,838** 个参数。只把最后一层换掉：

```python
model.fc = nn.Linear(model.fc.in_features, 102)   # 512 → 102
```

新分类头只有 **52,326** 个参数（$512 \times 102 + 102$），占总参数的 **0.47%**。

剩下 99.53% 的参数来自 ImageNet 的 120 万张图，那个模型认 1000 类日常物体，top-1 69.76%。

它学到的不是「花」，是**看东西的能力**：

- 浅层：边缘、颜色斑块、纹理方向
- 中层：花瓣轮廓、花蕊、叶片排列这类「部件」
- 深层：部件之间的组合关系

花卉分类要区分的，恰好是这些部件差异。把骨干搬过来，等于借了一套已经会「看」的眼睛，只需重新学「这 102 种花怎么分」。

这也是为什么归一化必须用 ImageNet 的 mean/std（`[0.485,0.456,0.406]`），不能用这批花自己的统计量——骨干是在 ImageNet 的数值分布上学会看东西的。

# 三、四组实验，只差一件事

| 组别 | 骨干 | 训练什么 | 轮数 | 增强 | 标签平滑 |
|---|---|---|---|---|---|
| scratch | 随机初始化 | 全部 1122 万参数 | 120 | 基础 | 0 |
| frozen | ImageNet | 只训分类头 5.2 万 | 12 | 基础 | 0 |
| two-stage | ImageNet | 先冻 5 轮，再全解冻 20 轮 | 25 | 基础 | 0 |
| strong | ImageNet | 同 two-stage | 5 + 35 | 强 | 0.1 |

设计意图：

- scratch vs frozen：只改「有没有预训练」，回答「借来多少」
- frozen vs two-stage：只改「要不要微调骨干」，回答「光借够不够」
- two-stage vs strong：只改「增强/平滑/训练长度」，回答「还能榨出多少」

第三组其实是**三因素捆绑**，不能归因到单一因素。

# 四、一次训练到底发生了什么

**第一步：分批。** 1734 张图不会一次全塞进去，而是打乱后切成 **28 批，每批 64 张**。

**第二步：前向。** 64 张图变成张量 `(64, 3, 224, 224)`，过骨干变成 `(64, 512)`，过分类头变成 `(64, 102)`——每张图对 102 个类各打一个分。

**第三步：softmax。** 102 个分数变成 102 个概率，和为 1。

**第四步：算损失。** 交叉熵只看「正确答案那一类的概率」，猜得越不准罚得越狠。第 1 个 batch 的 loss 是 **4.71**。

**第五步：反向 + 更新。** 算出每个参数该往哪调，AdamW 挪一小步。每批更新一次，28 批走完 = 1 个 epoch。

5 个 epoch 的真实记录：140 次更新，loss 从 **4.71** 降到 **1.52**。中间每个点都在抖：一批只有 64 张，梯度噪声大，但趋势向下。

**第六步：看它学没学会。** 固定 16 张测试图（每类一张），每轮结束看一次预测：

| epoch | 16 张里对几张 | 发生了什么 |
|---|---|---|
| 0 | 0/16 | 分类头是随机的，概率都在 3% 左右 |
| 1 | 1/16 | 开始有动静，但基本还在瞎猜 |
| 2 | 11/16 | 突然开窍，学会按颜色形状分大组 |
| 3 | 12/16 | 大组内继续细分 |
| 5 | 13/16 | 到 81.2%，和 frozen 整体水平一致 |

训练最开始，16 张图几乎全被判成同一种花（passion flower）。这不是 bug——随机初始化的分类头有偏置，模型先塌缩到少数类，再慢慢分化。第 5 轮时预测已分布在 14 个不同类别上。

# 五、结果怎么读

| 组别 | test top-1 | top-3 | macro-F1 | 最好的一轮 | 耗时 |
|---|---|---|---|---|---|
| scratch | 55.46% | 72.47% | 54.80% | 第 103 | 22.5 min |
| frozen | 81.27% | 92.11% | 80.45% | 第 8 | 2.0 min |
| two-stage | 92.50% | 97.69% | 92.14% | 第 24 | 4.0 min |
| strong | **92.96%** | 97.76% | 92.52% | 第 17 | 9.2 min |

**为什么 frozen 只用 2 分钟就到 81%？** 只动 5.2 万参数，其余 1100 多万个全部冻结，计算量几乎只有前向。

**为什么 two-stage 能到 92.5%？** 前 5 轮先冻骨干、把新分类头训到「不太离谱」，第 6 轮解冻全部参数，用很小学习率（$10^{-4}$，是分类头的十分之一）整体微调。这样骨干高层特征能针对花卉细调，不会被随机梯度冲垮。

**为什么 strong 只多 0.46%？** 强增强（裁剪下界 0.35、旋转、颜色抖动、RandomErasing）+ 标签平滑 0.1 + 35 轮，收益已经很小。这本身是个结论：这批数据上方法接近饱和。

**macro-F1 为什么比 top-1 低？** test 里有的类 238 张、有的类只有 20 张。macro-F1 对每类一视同仁，少数类差就会拉低它。四组差距分别是 0.66 / 0.82 / 0.37 / 0.43 个百分点——two-stage 之后差距变小，说明微调把弱类救回来一些。

# 六、模型在哪栽跟头

混淆矩阵按行归一化、按每类准确率升序重排后，**左上角就是最差的类**：

- **camellia（山茶）69.01%**，最常被认成 **mallow（锦葵）**
- **sweet pea（香豌豆）69.44%**
- **petunia（矮牵牛）70.17%**，test 里有 238 张，错得最多，对总体拖累最大

看错例图，9 张里 **4 张是 camellia → mallow**，模型还给出 0.57–0.999 的高置信度。两类都是「层叠花瓣 + 绿叶背景 + 单朵特写」，模型抓的是全局外观（大花瓣、高饱和颜色），没抓住花蕊与花萼这些细粒度线索。

还有一个疑似**标注噪声**的例子：`image_07303` 标签是 ball moss，模型以 0.908 置信度判成 foxglove。看图确实更像毛地黄，相邻的 `image_07304` 就标着 foxglove。这只是「很可能」，单张图无法定案。

# 七、工程上怎么保证数字可信

**1. 划分不能靠随机。** 原来用 `random.Random(0).shuffle`，但 Python 文档只保证 `random()` 序列跨版本稳定，不保证 `shuffle`。Kaggle 可能跑 3.11、本机 3.13/3.14，万一结果不同，云端与本地划分就对不上。改成对每个 `image_id` 算 `sha256("0:" + id)` 再排序取前 3 张——跨版本字节级一致，实测 3.11 / 3.13 / 3.14 三版指纹完全相同（`ce25c1c1…e81d`）：

```bash
python3 scripts/data_split.py --verify
```

**2. 产物契约钉死。** 每组必须产出 6 个文件：

```text
history.csv  metrics.json  per_class.csv
confusion_matrix.csv  misclassified.csv  top_confusions.csv
```

`metrics.json` 有 **70 个字段**，从 torch 版本、GPU 型号到 `split_fingerprint` 全记录。

**3. 交叉校验。** 混淆矩阵的迹除以 6149，必须等于 `test.top1`；`per_class` 的 `n_correct` 求和除以 6149，也必须等于它；错例行数算出的比例，还得等于它。三条独立路径互证，任一条对不上就是评估代码有 bug。

**4. test 只准评估一次。** 代码里有计数器，退出前断言等于 1。否则「反复在 test 上挑最好的一轮」就是作弊。

**5. 冒烟先于正式。** 正式跑四组要 39 分钟 GPU。先跑 CPU 冒烟（1 轮、3 个 batch），抓到三个本机发现不了的问题：

- Kaggle script kernel 的 `__file__` 在只读 `/kaggle/src`，写文件直接 `OSError`
- 数据集挂载路径猜错，找不到 `image_00001.jpg`
- 评估函数里按类累加用了 `+=`，102 个类加 64 个样本，shape 错误

第 3 个是纯逻辑 bug，本机没 torch 根本跑不出来。冒烟花 20 分钟，省下拿 30 小时配额去试错。

# 八、这套方法的边界

1. **只跑了一个 seed**，没有方差。two-stage 和 strong 差 0.46 个百分点，完全可能是噪声
2. **验证集只有 306 张**（每类 3 张），best epoch 选择本身有噪声：frozen 第 8 轮、two-stage 第 24 轮、strong 第 17 轮，换个划分可能就变
3. **loss 不能跨组比较**：strong 用了 label smoothing 0.1，它和其他三组不是一个尺度
4. **scratch 拿了最多 epoch**（120），所以它的劣势是**下界**——就算给更多轮，也只是更接近过拟合上限
5. **确定性别想太多**：`use_deterministic_algorithms(warn_only=True)` 只把「没有确定性实现」的算子从报错降成警告，不保证跨 GPU 位级一致。只承诺「同一会话、同一张卡、同一划分」下可复现
6. **公开结果不可直接比**：Nilsback 2008 的 72.8% 是 103 类旧库 + 手工特征；CCT 的 99.76% 是 from scratch Transformer；ViT-L 的 99.37% 是 303M 参数。没找到可核验的「ResNet-18 + 官方划分 + 全网络微调」一手结果，所以只做量级对照

# 九、如果继续做

1. **多 seed 重复**，报均值±方差，先确认 0.46% 到底是不是噪声
2. **针对弱类做平衡**：petunia、camellia、sweet pea 用类别平衡采样或 logit adjustment
3. **换骨干**：ConvNeXt-Tiny（27.9M）在同类任务能到 98%，代价是参数量 2.5 倍
4. **补类名与可视化**：把混淆对做成「两张图并排」的对照，比数字直观

# 一句话收尾

这个项目真正想说的不是「我做到了 93%」，而是：**在小样本细粒度任务上，预训练权重是性价比最高的那一件事——2 分钟、0.47% 的参数，换来 26 个百分点；而再往上每 1 个百分点，都要付出成倍的训练预算，并且开始撞上数据本身的噪声与不均衡。**
